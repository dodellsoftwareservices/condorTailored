# US venue connectivity and free market data

A read-only-first setup for the venues already supported by this checkout. The
catalog is `condor/us_venues.py`; the operator tool is `scripts/us_venues.py`.

**This is not a legal allowlist.** US/state/product/entity eligibility changes.
Check the venue's current terms and your own account permissions before enabling
a connector. A public endpoint being reachable does not make its products legal
or available to your account.

## Immediate answers: Lighter and Alpaca

### Lighter: save the credential in Hummingbot, encrypted

The easiest route is **Dashboard → Settings → Keys → Add API Key →
perpetual → `lighter_perpetual`**. Hummingbot asks for:

| Field | What to enter |
|---|---|
| `lighter_perpetual_l1_address` | Your Lighter L1 wallet address |
| `lighter_perpetual_api_key_index` | Numeric index of the API key |
| `lighter_perpetual_api_private_key` | The Lighter **API private key**, not your wallet seed phrase |
| `lighter_perpetual_account_limit` | Your account tier, normally `Standard` unless Lighter shows otherwise |

Hummingbot validates the connector and encrypts the file under its
`CONFIG_PASSWORD`. Its local storage is
`hummingbot-api/bots/credentials/master_account/connectors/lighter_perpetual.yml`;
**do not create or edit that YAML by hand** and do not replace its ciphertext
with plaintext. The file name is listed here only to explain where the encrypted
result lives.

`lighter` (spot) additionally asks for `lighter_account_index`. Testnet uses a
separate connector and a separate account/key: `lighter_perpetual_testnet` or
`lighter_testnet`. Never put mainnet credentials into a testnet line.

The API-private-key line is for the API credential generated by Lighter. Do not
enter an Ethereum wallet private key or recovery phrase unless Lighter's own
current documentation explicitly says that the generated value is one.

### Alpaca: save paper keys in `condor/.env`

```dotenv
ALPACA_API_KEY_ID=your_paper_key_id
ALPACA_API_SECRET_KEY=your_paper_secret
```

Generate these under **Paper Trading** in the Alpaca dashboard. The existing
`AlpacaPaperClient` pins `paper-api.alpaca.markets` and rejects the live trading
host. Paper and live credentials are different; the market-data plan attached to
an account is also a separate concern from whether its orders are simulated.

`.env` is gitignored. Do not paste either key into YAML, agent prompts, shell
history, issue reports, or source files. Restart Condor after changing this file.
Prefer exchange API permissions with withdrawals disabled and no unnecessary
trading scope.

## Connector lines

Blank import placeholders are in `.env.example`. You only need lines for venues
you actually use. For Hummingbot connectors, these variables are a **one-time
import source**, not the permanent credential backend.

```dotenv
# Lighter perps, mainnet (real-money credential; no orders are placed by import)
LIGHTER_PERPETUAL_L1_ADDRESS=
LIGHTER_PERPETUAL_API_KEY_INDEX=
LIGHTER_PERPETUAL_API_PRIVATE_KEY=
LIGHTER_PERPETUAL_ACCOUNT_LIMIT=Standard

# Coinbase Advanced Trade, mainnet
COINBASE_ADVANCED_TRADE_API_KEY=
COINBASE_ADVANCED_TRADE_API_SECRET=

# Kraken, mainnet
KRAKEN_API_KEY=
KRAKEN_API_SECRET=

# Gemini, mainnet
GEMINI_API_KEY=
GEMINI_API_SECRET=

# Bitstamp, mainnet
BITSTAMP_API_KEY=
BITSTAMP_API_SECRET=
```

The catalog also has Lighter spot/testnet lines. See `.env.example` for their
exact prefixes. Kraken's optional API tier uses Hummingbot's default; set it in
the dashboard instead if you need a non-default tier.

### Inspect without writing anything

From `condor/`:

```bash
uv run python scripts/us_venues.py status
uv run python scripts/us_venues.py status --check-data
uv run python scripts/us_venues.py status --venue lighter_perpetual --check-account
```

- `status` reads the local env and Hummingbot's credential-name registry.
- `--check-data` requests a small **public mainnet order book** per Hummingbot
  venue and checks that it is two-sided, sensibly priced, timestamped and fresh.
- `--check-account` performs an authenticated balance/account read only. It does
  not submit an order, transfer, withdrawal, or bot deployment.
- Lighter testnet rows use their mainnet data twins for research; testnet prices
  are never used as real-market opportunity prices.

### Import one credential explicitly

The dashboard is preferred. The equivalent CLI path is:

```bash
uv run python scripts/us_venues.py import --venue lighter_perpetual
uv run python scripts/us_venues.py import --venue alpaca_paper
```

The first writes through Hummingbot's encrypted credential API and then reads
balances. The second does **not** copy Alpaca keys into Hummingbot: it validates
the existing paper-only client's account read. Existing Hummingbot credentials
are not overwritten unless `--force` is explicitly supplied. All env values and
the API password are scrubbed from output, including upstream errors.

After importing a Hummingbot credential, remove its plaintext values from
`.env` if you do not need to repeat the import. Keep the variable names as blank
comments if you want a record of the setup. Restart running bots after changing
a credential; they keep the credentials with which they started.

## Free/simulated data coverage and limits

| Source | Free/read-only coverage | Authenticated simulation | Important boundary |
|---|---|---|---|
| Lighter via Hummingbot | Public crypto spot/perp books; candles where supported | Separate Lighter testnet account/key | Mainnet and testnet credentials/prices are not interchangeable |
| Coinbase Advanced Trade via Hummingbot | Public crypto books | No venue sandbox wired | Coinbase's public API is keyless; account data needs a key |
| Kraken via Hummingbot | Public crypto books/candles | No spot sandbox wired | Product availability varies by US state; no derivatives assumed |
| Gemini via Hummingbot | Public crypto books | No spot sandbox wired | Hummingbot connector support is not a state-eligibility claim |
| Bitstamp via Hummingbot | Public crypto books | Separate sandbox documented, not wired | Do not point the mainnet connector at a sandbox host |
| Alpaca | Stocks/ETFs, options and crypto data; paper account reads | Alpaca paper, stocks/options/crypto according to account support | **Basic stocks are IEX real-time, not all US exchanges**; options use the indicative feed; websocket and history limits apply |
| Yahoo Finance (`equity_market_data.py`) | Keyless research search, instruments and bars | None | Unofficial/delayed/rate-limited research feed; not execution-grade or consolidated |
| GeckoTerminal/CoinGecko | Keyless on-chain pool/token discovery | None | Pool data is not a CEX executable book; shared free-IP rate limits apply |

There is no single legal, free API that provides tick-level data for every US
stock, ETF, option, future, crypto asset and prediction market. Consolidated US
equity/options feeds generally carry exchange licensing fees. The free stack is
therefore a **watchlist of explicit feeds**, not a promise of complete market
coverage.

Kalshi is intentionally not listed as a working crypto/stock connector. It is a
CFTC-regulated event-contract venue with a demo environment, and this checkout
contains a `kalshi_perpetual` Hummingbot name, but that is not evidence of a
supported public event-market integration. Add it only after verifying the
current connector contract against Kalshi's official API.

## Arbitrage architecture: what “AI watches everything” should mean

Use deterministic collectors and calculations. AI can classify instruments,
explain reports and prioritize research; it should not invent prices, timestamps,
fees or legal availability.

1. **Discover and normalize:** instrument ID, venue, asset class, spot/perp,
   quote currency, multiplier, expiry, settlement, trading hours and timezone.
2. **Persist raw observations:** venue receive timestamp, exchange timestamp,
   sequence number, bid/ask depth and source. Deduplicate and enforce per-feed
   freshness limits before computing an opportunity.
3. **Match only economically fungible instruments:** spot to spot, or explicitly
   modeled derivatives. A perp/spot spread is a funding/basis trade, not a free
   cross-exchange spot arbitrage. Tokenized stocks and equities are not assumed
   fungible either.
4. **Price executable depth, not last trades:** walking both books for the actual
   order size is the starting point. Include taker/maker fees, spread, slippage,
   funding/borrow, transfer and gas costs, FX conversion, taxes where relevant,
   latency and expected rejection/fill probability.
5. **Account for inventory and settlement:** pre-fund both legs where possible,
   cap venue/asset/state exposure, and handle partially filled legs. Withdrawal
   support and transfer time are part of feasibility.
6. **Paper first, then bounded execution:** shadow quotes and simulated fills are
   useful but optimistic. Keep live execution separately authorized, kill-switched
   and outside the AI agent's unrestricted control.

### Working scanner

`routines/us_arb_scanner.py` now appears under **Routines → Arbitrage** after
reload. Its default compares 0.01 BTC-USD **spot** across Coinbase Advanced
Trade, Kraken, Gemini and Bitstamp. Coinbase uses the direct keyless public
adapter in `condor/public_books.py`; the other venues use Hummingbot.

It rejects simulation venues, mixed spot/perpetual scans, mismatched quote
currencies, stale/crossed/unsorted books and insufficient displayed depth. It
walks both books for the requested base quantity and subtracts both taker fees
plus a configurable latency buffer. Results are **modeled net**, not executable
or settled profit. Fee defaults are research assumptions only: set
`taker_fee_bps` from your actual account tier before drawing conclusions.

A live four-venue default scan was run read-only. All four books were accepted
and no route cleared the configured cost/buffer threshold. That is a negative
research result, not an execution failure.

Timestamp caveat: Hummingbot currently attaches local **snapshot** time to its
book responses (`services/market_data_service.py`), not the original exchange
update time. The scanner calls this snapshot age/skew. Only the direct Coinbase
adapter has a venue timestamp in this stack. Age/skew checks are therefore
necessary but not a substitute for sequenced websocket collection and measured
clock offsets.

The older `routines/arb_check.py` remains a generic gross-spread/depth viewer.
It is not the conservative scanner and should not be used as evidence of
executable profit. Never compare a stock with a crypto perp, or a perp with a
spot asset, and call the raw difference arbitrage.
